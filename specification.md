# CLAUDE.md

This file guides Claude Code when working on **LoonieToonie**. The full specification is in `specification.md`. Read it before starting a new phase.

## What the app does

LoonieToonie is a household expense app. Users scan receipts, track spending, and see their spending habits so they know how much they can save.

Current priorities:
1. Scan multilingual receipts (English, Japanese, etc.) and get the **date, items, prices, and currency** right.
   - Default currency: **USD**. Users can change it on the review screen.
2. Assign a category to each item based on its name.
3. Show items with their categories and prices, sorted by date.

## Architecture rules

- **No own database server for financial data.** All user data lives in the user's **LoonieToonie** spreadsheet and Drive folder. Do not add Postgres, SQLite, etc. without asking. See [Storage roadmap](#storage-roadmap) for the planned exceptions.
- **All storage access goes through one interface** (`backend/app/storage/`): a `Repository` protocol with `SheetsRepository` now. Routes and services must never call `gspread` directly. This lets us add a local cache or a `PostgresRepository` later without touching business logic.
- **OAuth scope stays `drive.file`.** Never request broader Drive/Sheets scopes.
- **OCR runs on the device.** By default, only OCR text goes to Claude. Send the image to Claude only as a single retry when validation fails.
- **Claude output must be strict JSON**, enforced with tool use / structured output. Validate it on the backend:
  - item prices (× quantity, minus discounts/plus tax) add up to the total
  - the date is valid
  - the currency is set (default `USD`)
  - each category exists in the user's `categories` tab
- **IDs are UUIDs** generated by the backend.
- **Respect Sheets API quotas** (~60 reads + 60 writes/min per user): batch writes with `append_rows`, cache reads, and never write row by row in a loop.
- Compute summaries in Python (pandas) after loading the tabs. Sheets has no joins or SQL.
- The React code calls one OCR function on every platform. Platform differences stay inside `frontend/src/ocr/`.

## Spreadsheet schema (tabs)

| Tab | Columns |
| --- | --- |
| `receipts` | receipt_id, store, purchased_at, total, currency, image_link, created_at, updated_at, deleted |
| `items` | item_id, receipt_id, name, quantity, price, category, updated_at, deleted |
| `categories` | name, icon, updated_at, deleted |
| `budgets` | month, category, amount, updated_at, deleted |
| `settings` | key, value, updated_at |
| `ocr_labels` | receipt_id, field, model_value, corrected_value (opt-in) |

- `updated_at` (ISO 8601 UTC) and `deleted` (soft-delete flag, `TRUE`/`FALSE`) exist on every synced tab, so a local cache can sync later with last-write-wins. Never hard-delete rows. Set `deleted = TRUE` instead.
- If you change the schema, update `specification.md` and handle existing spreadsheets (migration on login).

## Storage roadmap

| Stage | When | Storage | Notes |
| --- | --- | --- | --- |
| 1 | Now (phases 1–5) | Google Sheets only | Simple, free, user-owned data |
| 2 | Phase 6 (dashboard) or when speed matters | + on-device cache: Capacitor SQLite (`@capacitor-community/sqlite`) on Android, Dexie/IndexedDB on web PWA | Instant loads + offline. Sheets stays the source of truth; sync with `updated_at` / `deleted` (last-write-wins) |
| 3 | Bank/card linking (phase 10) | + small **encrypted server-side token store** (server SQLite with backups, Supabase/Neon free tier, or Google Secret Manager) | Holds only `user_id`, encrypted Plaid/Flinks access tokens, Google refresh token, spreadsheet ID. **No financial data.** Bank transactions are still appended to the user's Sheet (dedupe by `transaction_id`) |
| 4 | Only if needed: sharing between users (family budgets), many users, or Sheets limits | Migrate to **PostgreSQL** (managed, Canadian region preferred) via `PostgresRepository`; Sheets becomes an export/sync option | Requires the privacy checklist below |

Rules:
- Never store bank tokens or other secrets in the user's Google Sheet.
- Don't move to stage 4 without explicit approval. It changes the app's privacy promise.

Privacy checklist if financial data ever lives on our servers (stage 4):
- TLS in transit, encryption at rest, extra column-level encryption for tokens and sensitive fields
- Row-Level Security (each user reads only their own rows)
- Minimal data: no bank passwords (aggregator only), no full card numbers, no receipt images in the database
- Two-factor authentication option for logins
- Data export + full deletion on account removal; limited backup retention
- PIPEDA / Quebec Law 25 compliance; clear privacy policy that says we never sell data or show ads

## API endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/auth/google`, `/api/auth/callback` | Google Sign-In |
| POST | `/api/receipts/scan` | OCR text (+ image) → Claude → draft receipt |
| POST | `/api/receipts` | Save confirmed receipt + items |
| GET | `/api/receipts` | List (filters: date, category) |
| PUT / DELETE | `/api/receipts/{id}` | Edit / delete |
| GET / PUT | `/api/budgets` | Monthly budgets per category |
| GET | `/api/summary?period=month` | Totals, by-category, budget vs actual, saved amount |
| POST | `/api/chat` | Spending chatbot |
| GET | `/api/export/csv` | CSV export |

## Frontend

- Pages: Home, Scan (capture → review/edit → save), Transactions, Dashboard, Budget, Settings.
- PWA: manifest + service worker. Users can view past data offline (IndexedDB cache is optional).
- UI style: simple and friendly, with cute icons and a girl mascot character.

## Secrets and config

- Use `backend/.env` and `frontend/.env`, and commit `.env.example` files only. Never commit real keys.
- Required: Anthropic API key, Google OAuth client ID/secret, a Google Cloud project with the Sheets + Drive APIs enabled, and a Cloud Vision key (web fallback only).

## Development phases

Work on **one phase at a time** and wait for confirmation before starting the next.

1. Scaffold: `frontend/` (Vite React PWA + TS), `backend/` (FastAPI), Docker Compose, `.env.example`
2. Auth: Google Sign-In (`drive.file`)
3. Storage: create the LoonieToonie spreadsheet + tabs on first login; `Repository` interface + `SheetsRepository`
4. Receipts CRUD (manual entry first)
5. Scan flow: Capacitor ML Kit OCR + Claude parsing + review page
6. Dashboard & budgets (+ on-device cache if loading is slow; storage roadmap stage 2)
7. Chatbot
8. CSV export
9. Capacitor Android build (needs Android Studio locally)
10. Later: bank/card linking (Plaid / Flinks) with an encrypted token store (storage roadmap stage 3), saving/investment suggestions

## Conventions

- Backend: type hints everywhere, Pydantic models for request/response and for the Claude JSON schema, and pytest for tests. For the receipt parser, test with sample OCR texts in several languages.
- Frontend: TypeScript strict mode, functional components and hooks.
- Store money as decimal values with an explicit currency. Never use floats for totals in calculations.
- Store dates as ISO 8601 (`YYYY-MM-DD` for purchase dates).
